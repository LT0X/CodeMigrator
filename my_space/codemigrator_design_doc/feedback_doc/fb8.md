二、“我们的确定性脚本弱”——补强已落地
对照后发现我们真正缺的不是解析深度（tree-sitter 比 kit 的正则脚本强得多），而是那条运行时对抗审计闭环。已写入 M-06 新节「完备性对抗审计」：

机械层产出后、CreateRun 签核前：双怀疑派评审（独立上下文、不相交抽样[随机半+对抗指派半]）→ 每样本从源码列 file:line 证据行（不是结论）→ 与机械产物双向 diff（漏判/多判）→ 确认差异 = 修提取规则不修结果 → 重生成换样重抽 → 三轮失败或同类复发升级你决策（通常意味着不可静态发现）。审计记录随计划证据归档。

另显式成文一条既有优势：SCC/环拒绝在模块粒度执行（F2 直接落模块级），天然覆盖 kit “文件级查完还要收缩到分包再查”踩过的坑（Bun 的 1.6 万编译错误正是这么来的）。这与静态金标准条款 V-M06-V4-019 形成“规则正确性 × 单次运行质量”双保险。

三、“他们数百 agent 并发，我们为何个位数”——三池模型已升格
根因：旧资源公式把三种异质资源捆在一池。已拆分（M-00 并发执行模型 + M-09 资源节同步重写）：

池	内容	约束
模型会话池	Slice 会话的 LLM 调用 + 只读工具（ReadFile/QuerySourceAst/Exec 只读编排）——不经沙箱	provider 配额 + Run 预算，可数十路扇出
沙箱执行池	Shell/Scaffold 的 bwrap 实例，按需取用、用毕归还（卷与缓存保留）	物理公式 max(1, min(4, mem/4, cpu/2)) 只约束同时活跃 bwrap 位
裁决派发池	InternalVerificationDispatch 检查	active-attempt gate（现状）
任一池耗尽只阻塞对应类别动作，不冻结整个会话。安全性不减——bwrap 本来就只该罩不可信执行，模型调用和只读导航在 app 进程内本无隔离需求。V-M09-V4-014 同步重写。
