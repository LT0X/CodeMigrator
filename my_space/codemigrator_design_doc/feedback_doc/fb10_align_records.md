## 1. 议题一：扇出探索的协调机制

### 1.1 fb10 矛盾定位

现行 V5 设计（M-16/align\_records）：Harness 读 PSF 图谱确定性切域 → 派发 N 个只读探索子会话 → 主会话单点归并。用户三点质疑：

1. **机械域与语义内聚错位**：切域依据是 F1 模块清单 + PSF-3 关系图 + 描述符 `module_boundary_strategy`（目录/清单边界），而代码的语义内聚（如"配置解析逻辑散落三个目录"）可能跨机械域——确定性切域是否可靠？
2. **扇出提示词静态化**：探索员收到的是固定模板 + 域指派，高风险域与纯工具域同权重探索，无法按域特征定向。
3. **是否需要模型协调/常驻主 Agent**：主会话模型是否应参与协调？是否应常驻协调整个 CodeMigrator 各阶段？该架构是否应提升到系统层面？

### 1.2 候选方案与对齐过程

| 方案           | 内容                                                                                | 权衡                                     | 对齐结果                   |
| ------------ | --------------------------------------------------------------------------------- | -------------------------------------- | ---------------------- |
| A：维持现状       | Harness 确定性切域，提示词固定模板                                                             | 零模型依赖；但语义错位与静态提示词疑虑保留                  | 否决                     |
| B：Planner 范式 | 机器出骨架（F1/PSF-3 确定性域）→ 模型调形状（合并/拆分/重点标注+每探索员 focus brief）→ 机器校验（覆盖恰好一次+扇出/预算上限）后派发 | 与 V5"确定性裁判、LLM 建筑师"同构，机制最小增量           | 被吸收进形态 2               |
| C：常驻主 Agent  | 系统级常驻模型会话协调全周期                                                                    | 全局协调最强；推翻 P-01 扇出权、单写者模型、每任务一会话，V6 级重构 | 用户明确不怕量大、要探讨可行性 → 深化对齐 |

**常驻形态专项对齐**（三形态）：

| 形态                  | 内容                                      | 评估                                  |
| ------------------- | --------------------------------------- | ----------------------------------- |
| 1：单一常驻 Orchestrator | 一个 Reasoning 会话贯穿 Run 全周期观察全部事件出 advice | 协调力最强；单点、上下文无界、advice 采纳规则难枚举——最不优雅 |
| **2：分阶段常驻（选定）**     | 每阶段一个常驻协调会话 + 每任务工作会话；阶段间经审计事实交接        | 职责单一、上下文有界、与现有会话模型平滑衔接              |
| 3：事件触发协调会话（无常驻）     | 定义触发事件集，触发时开会话出建议后关闭                    | 改动最小；动态扇出调整弱                        |

### 1.3 决策：形态 2 分阶段常驻

* **起草期**：主会话升级为**探索协调者**——持切域调整权（机器骨架 → 模型调形状 → 机器校验的 Planner 范式，方案 B 融入）+ 动态改派探索员（读增量报告后调整未完成探索员的任务简报）。

* **EXECUTE 期**：**Slice Supervisor** 常驻协调（职责见 1.4 精简版）。

* **共同边界**：均只出建议（advice）、actor 白名单采纳；VERIFY/REPORT 零模型硬边界不破（任何形态都不得介入）；P-04 单写者保持。

### 1.4 Supervisor 精简定案（用户主动砍除过度设计）

对齐中给出六条触发事件集，用户判定其中四条为过度设计（"现在模型的性能都很强了，尽可能的优雅一下"），精简为**两触发两职责**：

**保留**：

1. **归因多义/双错**（机械归因候选修复集 >1，含守恒辅助排序后仍多义）→ 全局修复决策（议题三核心）
2. **Slice 会话失败停止**（provider 终态失败/会话级不可恢复错误）→ 异常语义路由建议

**砍除**：~~工具拒绝风暴~~、~~重试风暴~~、~~系统性误译信号自动蒸馏~~、~~卡滞预警~~。经验蒸馏回归现行归因驱动的规则手册追加通道（M-00 既有机制，零新增）。

**观察模型：被动唤醒式常驻**（响应用户"不可能所有情况都观察，上下文都满了"）：

* **基线层**：态势快照——机器从 run\_events 派生的低基数结构化投影（各 Slice 状态计数、阶段、异常计数），持续计算但**不进模型上下文**，仅唤醒时注入，零常驻成本。

* **唤醒层**：触发条件命中时唤醒，注入态势快照 + 本次决策相关的**定向事件投影**（相关 Slice 上下文、验证 receipt、归因证据），有界。

* **滚动摘要**：历史唤醒记录蒸馏为有界滚动窗口——"常驻"仅指会话上下文跨触发连续，而非持续消费事件流。

## 2. 议题二：知识图谱构建时序与使用面

### 2.1 fb10 矛盾定位

M-16 说起草会话（CreateRun **之前**）"消费预索引知识图谱（PSF 投影）"；但 M-06 分析流水线（F1～F4 + PSF-2/PSF-3 投影的唯一产地）挂在 ANALYZE 阶段（CreateRun **之后**）。图谱到底何时首次构建？用户据此质疑"ANALYZE 的导航图辅助不了最初的探索阶段"——鸡生蛋矛盾。

**使用面澄清**（对齐材料，现行设计本就覆盖三期）：起草扇出（探索员 QuerySourceAst 查 PSF-2）、PLAN（Planner 消费 PSF-2/3 事实）、EXECUTE（QuerySourceAst 是六工具之一）。真正缺的是"首次构建时点"的显式契约。

### 2.2 候选方案与决策

| 方案                          | 内容                                         | 对齐结果   |
| --------------------------- | ------------------------------------------ | ------ |
| **A：构建前移 + ANALYZE 复用（选定）** | 项目注册/起草会话开启时即对冻结快照跑机械完备层管线；ANALYZE 改为复用+校验 | **选定** |
| B：起草期轻量索引 + CreateRun 后完整重建 | 两次解析、两套口径、等价性验收负担重                         | 否决     |
| C：维持现状隐含两次独立分析              | 鸡生蛋矛盾未解                                    | 否决     |

### 2.3 决策详则

* **首次构建时点**：项目注册 / 起草会话开启时（探索开始前必须可用，形态 2 的探索协调者与探索员都依赖它）。

* **投影键与生命周期**：键 = snapshot OID + 描述符摘要；属 M-00"可重建投影"类（7 天留存，可按冻结 commit 重建）。

* **三期消费同一投影**：起草扇出、Planner、EXECUTE QuerySourceAst——"索引一次、处处复用"（与 codegraph 实践一致，fb10 引用参照）。

* **ANALYZE 职责重定义**：CreateRun 后不再重复解析，改为三件事——复用既有投影、冻结校验（与 Spec 锁定描述符摘要一致）、与已确认 UnderstandingDossier 的一致性校验（偏差记入分析投影，不回写工件，现行语义保留）。

### 2.4 流程增强（对齐中用户新增）：探索完成后的多轮提问对齐

用户提出："是不是在 agent 探索完项目后再对用户进行提问工具对齐，提问工具对齐很重要不用限制次数，前期的对齐关乎到整个系统的运行。"

* **流程重排**：探索扇出完成 → 主会话（探索协调者）归并报告（含冲突/风险热点/语义模块划分建议）→ **基于归并发现的多轮 AskUser 对齐**（逐项对齐语义模块划分、依赖判定分歧、风险处置、测试策略、蓝图原则）→ 对齐结论固化为四件工件草稿 → 试译校准（既有）→ 用户显式确认冻结。

* **对齐轮次定案**（二次对齐收敛）：**全周期（起草 + 运行期）不设硬性次数上限，由协调会话按需自主判断是否继续对齐**（用户原话："肯定是根据情况来 agent 自己选择是否还需要对齐的次数，肯定不限制次数"）；取消现行"一次最多三题"式框架限制（每题质量标准——QuestionId、互斥选项、推荐项、影响说明——不变）。

* **与"前期做足、后期放手"的关系**：放手仍指不逐 Slice 确认（硬确认门仍收敛为四工件确认 + ImpactPreview 两处）；软性 AskUser（澄清/风险决策）由 agent 自主发起，全周期可用。

## 3. 议题三：跨 Slice 返工归属与修复上下文

### 3.1 fb10 矛盾定位

场景：A（models）已集成 verified（rank 2），B（api）依赖 A（rank 6）。用户四点质疑：

* (a) 双错怎么办？现行"唯一归因→仍多义→Run 终态兜底"= 双错死路，"十分复杂""拧巴、生硬、不简洁优雅"。

* (b) write scope 如何确定？"谁出错就由它全面接手"是否可行？

* (c) B 因 A 出错时，A 的修复会话没有 B 的上下文——是否需要重读？上下文压缩考虑了吗？

* (d) 最终集成测试失败的返工归属哪些 Slice？

### 3.2 问题本质重新定位（对齐中确立的核心洞察）

**V5 把「读视野」与「写权限」绑死了**：可读根 ⊆ 本 Slice 上下文（M-12），write scope 互斥（M-07）。隔离设计为**并行生成**服务（防串扰、防"测试向实现看齐"），对初译正确；但**修复是另一种活动**——失败暴露的是跨 Slice 交互的语义裂缝（B 的调用 × A 的实现 × 测试的期望），修复决策天然需要整体视野（用户："代码肯定是整体意识的"）。"A 不知道 B、B 不知道 A"的根源不是 write scope，而是**读视野被写权限绑架**——架构层耦合错误，即"拧巴"来源。

### 3.3 候选方案与对齐过程

| 方案                     | 内容                                 | 对齐结果                                          |
| ---------------------- | ---------------------------------- | --------------------------------------------- |
| A：维持现状                 | 唯一归因门；双错/多义→Run 终态兜底               | 否决（死路）                                        |
| B：最小修复集                | 归因输出 Slice 集合，按依赖序串行重生成，各修各域       | **用户否决**："最小修复集很不优雅，A 不知道 B、B 不知道 A，代码是整体意识的" |
| 读写分离 + Supervisor 修复决策 | 修复会话全境读+本域写；Supervisor 读全局出修复决策    | **方向认可**（"方向趋势是对的"）                           |
| 载体：全局修复会话（新专门 agent）   | Supervisor 派发新会话持联合域写+全境读，不属于原 A/B | **选定**（两级路由）                                  |

### 3.4 决策：读写分离 + Supervisor 修复决策 + 两级路由

**核心原则：修复会话全境读、本域写（Repair Session: Global Read, Scoped Write）——读视野与写权限解绑。**

**修复执行链路**（响应用户两次身份澄清追问：Supervisor 不写代码；修复者是 Supervisor 派发的新专门 agent 而非原 A/B）：

```
验证失败（集成/最终）
  → 机械归因：证据落点 file:line → write scope 查表 → 候选修复集（集合而非唯一）
      │
      ├─ 唯一命中单 Slice 且无强耦合信号 → 简单：原 Slice 重生升级包
      │   （现行 generation 机制 + 升级包：全境读视野 + 修复简报；Supervisor 零介入零开销）
      │
      └─ 任一复杂条件命中 → 升级 Supervisor：
            ① 多义：证据落点跨多个 write scope（双错/交互错）
            ② 守恒辅助排序后仍多义（现行"→Run 终态兜底"死路改为升级入口）
            ③ 同类失败跨 generation 复发（重生后同类错误再现＝修复视野不足信号）
            ④ 强耦合信号：证据同时涉及接口签名定义处与其调用处
            ↓
        Supervisor 读整体现场（全境只读：修复集已集成代码+失败测试+调用链+期望vs实际）
            → 修复决策：最终修复集 + 域分配（改A/改B/都改）+ 每会话修复简报
            → actor 白名单校验采纳（write scope 合法性/预算/安全）
            → 派发【全局修复会话】执行
```

**角色分工**（澄清定案）：

| 角色                 | 类比      | 读                  | 写                    |
| ------------------ | ------- | ------------------ | -------------------- |
| 机械归因（M-10）         | 事故鉴定员   | 证据落点               | —                    |
| EXECUTE Supervisor | 总监理/架构师 | 全 Run 全局           | **零**（只出决策建议）        |
| 全局修复会话 / 重生会话      | 持图纸的施工队 | **修复集全境**（读写分离升级点） | 本域 / 联合域 write scope |
| Run actor          | 安全员/发令者 | 控制面                | 决策采纳（白名单）            |

**全局修复会话定义**（载体终策：两级——重生+全局修复会话）：

* **身份**：Supervisor 派发的新会话，身份 = (run\_id, repair\_decision\_id)，**不属于原 Slice A/B**。

* **读**：全 Run verified 树 + 源快照 + 失败测试全文 + PSF-2 调用链 + 修复简报。

* **写**：修复集联合域（修复集内 Slice 的 write scope 并集）。**安全条件**：并集内路径无其他在途并行写者——修复集全集成时天然满足。write scope 互斥的目的本是防并行写冲突，联合域是**条件安全**的精化，不是破坏不变量。

* **代次**：不占原 Slice 的 generation 0-2（修复不是重做初译）。

* **验证**：checkpoint → 局部验证 → 集成验证 → verified 前推（走现行三层路径）→ 对新 head 重跑最终验证。

**路由判据**：全部机械可判定（查表+计数），零模型消耗，发生在机械归因后、由 actor 判定，Supervisor 不参与路由本身。

**确认门定案：免确认门**。全局修复会话与现行 generation 重生同待遇——归因驱动的内部闭环，不走 ImpactPreview 确认门（区别于用户发起的契约漂移/结构修正=设计级变更走确认门）；修复决策全量进 run\_events 审计；Supervisor 判断有歧义/风险时可建议 actor 触发 AskUser（对齐轮次自主不限次，议题二已定）。

**终态兜底次序变更**：现行"仍多义→Run 终态"改为"升级 Supervisor → 全局修复先试 → 实在修不好才终态失败"——直接化解 fb10"双错=死路"的批评。

**返工归属（问题 d）**：最终集成测试失败走同一机制——证据落点 → 候选修复集 → 两级路由 → 简单重生 / 全局修复。归属不再是预先规定的"哪些 Slice"，而是 Supervisor 决策的修复集。

### 3.5 上下文压缩增强（响应追问③"上下文压缩的设计有考虑吗"）

现行 M-14 四件机制（水位逐出为结构化摘要、不可逐出集合、大对象外置 CAS + `cas://` 取回、provider 精确 token 计数）对 Slice 会话执行期**够用，不变**。V6 新增两处：

1. **全局修复会话初始装配**：全境上下文不一次性装满——修复简报为必要输入（不可静默截断），其余以**导航索引**形态给出（涉及文件 + 位置清单），Agent 按需 ReadFile 拉取；超限部分外置 CAS 按需取回。
2. **Supervisor 滚动摘要**：常驻观察流不无限累积——近期唤醒保详情、远期蒸馏为摘要、有界滚动窗口；观察成本受独立预算档治理。

## 4. 收官议题：Harness 与主 Agent 的关系（三层架构）

对齐收官时用户追加全局问题："还得全局思考一下 harness 和主 agent 的关系。"定案：

### 4.1 三层架构

```
┌─────────────────────────────────────────────┐
│        Harness（runtime / Run actor）         │
│   权力层：确定性控制面 · 单写者 · 全部决策权     │
│   状态机 / 事务 / 调度 / 安全边界 / 恢复        │
└──────────────┬──────────────────────────────┘
       ↑ advice（白名单采纳）        ↑ 回执/命令/事件（邮箱既有消息）
  ┌────┴──────────────┐              │
  │  常驻主 Agent（判断层）│             │
  │  起草期：探索协调者    │              │
  │  执行期：Supervisor  │              │
  │  跨域视野·设计判断·零权力│             │
  └───────────────────┘              │
                          执行层：工作会话（探索员/Slice 会话/全局修复会话）
                          各域施工 · 域内写 · 升级读
```

| 维度 | Harness（actor）           | 常驻主 Agent              |
| -- | ------------------------ | ---------------------- |
| 本质 | 权力层：确定性控制面               | 判断层：语义协调面              |
| 拥有 | 状态机、事务、调度、安全、**全部决策权**   | 跨域视野、设计判断、**零直写权**     |
| 输入 | 完整控制面事实（命令/回执/事件）        | 态势快照 + 定向事件投影（受控观察）    |
| 输出 | 事实变更（状态/ref/事件）          | advice（actor 邮箱新消息类型）  |
| 记忆 | PostgreSQL/Git/CAS（持久真相） | 滚动摘要（会话连续性，可从事件流重建）    |
| 失效 | 系统不可用（重启恢复）              | **退化为 V5 机械路径**（控制面完好） |

### 4.2 三条关系原则

1. **权力单向、建议两级**：

   * **约束内建议**（actor 自动采纳）：修复决策（write scope 校验过即执行）、探索员改派（域覆盖校验过即执行）——机械校验兜底，无人值守不打断。

   * **边界性建议**（actor 转化或拒绝）：PlanRevision 建议、AskUser 建议——涉及冻结事实，走既有确认门/提问通道。
2. **主 Agent 是增益层不是依赖层**：控制面完整性与 V5 完全相同；判断层缺席（模型故障/预算耗尽）系统照常运行，退回机械归约——优雅降级是核心保障，主 Agent 不成为新单点。
3. **类比定位**：Harness = kernel（拥有一切），主 Agent = 建议型 daemon（有能力、无权限），工作会话 = 受限域内 user processes。三层各司其职，无双重指挥。
