## 0. 反馈摘要

本轮反馈提出 **5 项方向性调整意见**，其中第 1 项为项目定位重定向，第 2-4 项为对当前架构核心机制的直接否定，第 5 项为整体架构可能需要大改的判断。这些意见之间有内在逻辑联系：定位变更导致部分核心机制的设计前提不再成立。

## 1. 项目定位重定向：聚焦跨语言迁移

### 反馈原文

> "项目定位为跨语言迁移的实现，同语言的更新和迁移通用 agent 以及做得很好了"

### 详细说明

当前 V3 架构文档将 CodeMigrator 定位为"迁移类型无关的通用代码迁移 Agent"（D-004），设计文档中以"React 16 → React 19"等**同语言框架升级**作为贯穿场景。

用户认为这一定位存在问题：

| 迁移类型 | 当前通用 Agent 能力 | CodeMigrator 的差异化价值 |
|---|---|---|
| 同语言框架升级（React 16→19） | ✅ Claude Code / Cursor 等已能很好处理 | ❌ 无明显差异化 |
| 同语言版本升级（Python 2→3） | ✅ 通用 agent 表现良好 | ❌ 无明显差异化 |
| 同语言 API 迁移（axios→fetch） | ✅ 通用 agent 表现良好 | ❌ 无明显差异化 |
| **跨语言迁移（TypeScript→Python）** | ⚠️ 通用 agent 难以系统性处理 | ✅ **这是本项目的核心价值** |

### 定位调整方向

CodeMigrator 应**聚焦跨语言代码迁移**作为核心定位：

- **不做**：同语言内的框架升级、版本升级、API 迁移——这些通用 agent 已经做得足够好
- **要做**：跨语言翻译（TypeScript→Python、Java→Go、Python→Rust 等）——这是通用 agent 难以系统性完成的领域

### 对架构的影响

这一定位变更**不是简单换示例**，而是影响架构核心机制的设计前提：

| 当前机制 | 为同语言迁移设计的前提 | 跨语言定位下是否仍成立 |
|---|---|---|
| NodeLocator 指向源文件，patch 也在源文件 | 源和目标是同一棵 AST | ❌ 不成立：源语言和目标语言是不同的 AST |
| GuardedPatch 做同文件内字节替换 | 修改已有代码结构 | ❌ 不成立：需要创建全新的目标语言文件 |
| Rule 操作（REPLACE_CAPTURE 等）在捕获上做变换 | 在已有 AST 节点上做结构替换 | ⚠️ 部分成立：但跨语言需要"读取源语言 AST → 生成目标语言代码" |
| 字节级 precondition_hash 验证 | 同一文件内的并发写入保护 | ❌ 冗余：详见第 4 点 |

## 2. 五阶段执行阶段原语表达能力质疑

### 反馈原文

> "五阶段执行阶段原语是否表达能力足够以及是否不够灵活，这一部分还需要探讨"

### 详细说明

当前 M-05 定义的规则操作（operation）只有四种：

```
REPLACE_CAPTURE    — 替换捕获内容
INSERT_BEFORE      — 在捕获位置前插入
INSERT_AFTER       — 在捕获位置后插入
DELETE_CAPTURE     — 删除捕获内容
```

这些原语是为**同语言内的 AST 节点变换**设计的。在跨语言迁移定位下，存在以下表达能力问题：

### 2.1 原语粒度是否足够？

跨语言迁移需要的操作可能包括：

| 跨语言操作需求 | 当前原语能否覆盖 | 说明 |
|---|---|---|
| 将 TypeScript 函数翻译为 Python 函数 | ⚠️ REPLACE_CAPTURE 可替换内容，但无法表达"从源语言 AST 生成目标语言代码"的语义 | 原语只表达"在哪个位置做什么变换"，不表达"如何翻译" |
| 创建全新的目标语言文件 | ⚠️ INSERT 到空文件，但语义不清晰 | 原语面向"已有 AST 上的变换"，不是"从零生成" |
| 删除源语言文件 | ❌ 无对应原语 | 当前架构没有"删除整个文件"的 operation |
| 重命名文件（.ts → .py） | ❌ 无对应原语 | 当前架构没有"文件级重命名"的 operation |
| 批量生成目标语言项目结构 | ❌ 无对应原语 | 跨语言迁移可能需要生成新的 package.json、requirements.txt、目录结构等 |

### 2.2 原语是否过于刚性？

当前原语是"位置 + 变换"模型，适合精确的 AST 节点操作。但跨语言迁移可能需要：

- **语义级变换**：不是"替换这个节点"，而是"理解这个函数的语义，生成等价的目标语言实现"
- **上下文感知生成**：目标代码的生成可能依赖源代码的整体上下文（类型系统、模块结构、异步模型），而非单个节点
- **多文件协同生成**：一个源语言文件可能映射到多个目标语言文件，或多个源文件合并为一个目标文件

### 待探讨问题

- 是否需要增加"文件级操作"原语（CREATE_FILE、DELETE_FILE、RENAME_FILE）？
- 是否需要增加"跨语言生成"原语（TRANSLATE_CAPTURE、GENERATE_TARGET）？
- 是否需要将原语从"AST 节点变换"扩展为"语义变换 + 代码生成"？
- Agent 的 edit intent 格式是否需要重新设计以支持跨语言表达？

## 3. "Agent 不能直接写代码"理由的否定

### 反馈原文

> "关于'Agent 提案 vs Host 执行'部分，中为什么 Agent 不能直接写代码？——三个关键理由，1 安全——不可信数据不能成为指令和确定性，首先这一点无从认可，现在百分之90以上的代码都又agent大模型书写，这一方面表现很好了，因为安全和确定性就不让agent直接写代码不成立，权限最小化——Agent 不能绕过约束，这一部分是我们这个项目特定领域harness要考虑的问题，不能因为这个成为理由"

### 详细说明

当前架构（P-01 原则）的核心设计是：

```
Agent 只有提案权 → 输出类型化 edit intent（不含替换文本）
Host 受信编辑链 → 插件 EmitPatch 生成 GuardedPatch（含替换文本）→ 字节级写入
```

这个设计基于三个理由，用户**逐一否定**：

### 3.1 "安全——不可信数据不能成为指令" → 用户否定

| 架构文档的论点 | 用户的反驳 |
|---|---|
| Agent 输出是不可信数据，不能成为指令 | 现在 90% 以上的代码都由 agent/大模型书写，这方面表现已经很好了 |
| 防止代码中的"忽略规则"文字变成指令 | 这个安全担忧在实践中已被证伪——大模型直接写代码是可行的 |
| closed schema 校验防止幻觉 | 模型直接写代码的可靠性已经足够 |

**用户的结论**：以"安全"为由不让 Agent 直接写代码不成立。

### 3.2 "确定性" → 用户否定

| 架构文档的论点 | 用户的反驳 |
|---|---|
| 模型可能产生幻觉、定位错行号、替换文本写错 | 大模型直接写代码的确定性在实践中已经足够 |
| Host 的 precondition_hash + post-parse assertion 提供确定性保证 | 这些机制本身的复杂度可能超过其带来的收益 |

**用户的结论**：以"确定性"为由不让 Agent 直接写代码不成立。

### 3.3 "权限最小化——Agent 不能绕过约束" → 用户否定

| 架构文档的论点 | 用户的反驳 |
|---|---|
| Agent 能直接写代码就可以绕过 write scope、写 .git、写其他 Slice worktree | 这是项目特定领域 harness 要考虑的问题 |
| 通过 Agent 只有提案权来保证权限最小化 | 不能因为这个成为不让 Agent 写代码的理由 |

**用户的结论**：权限最小化是 harness 层面的约束问题，不应该通过剥夺 Agent 写代码能力来解决。

### 对架构的潜在影响

如果接受用户的观点，Agent 可以直接写代码，那么：

| 当前机制 | 是否还需要 |
|---|---|
| 类型化 edit intent（不含替换文本） | ❌ 不需要，Agent 直接输出代码 |
| 插件 EmitPatch 生成 GuardedPatch | ⚠️ 可能简化或去除 |
| precondition_hash 字节级验证 | ❌ 不需要（详见第 4 点） |
| post-parse assertion | ⚠️ 可简化为编译验证 |
| Host 受信编辑链的 8 步流程 | ⚠️ 大幅简化 |
| 插件 ResolveLocator 重定位 | ⚠️ 可能仍需要定位能力，但不需要生成补丁 |

**这等于推翻了 P-01 原则和 M-08 代码修改引擎的核心设计。**

## 4. 字节级哈希验证为冗余设计

### 反馈原文

> "关于通过字节比较哈希的设计，我们定位已经是跨语言迁移项目代码了，字节级别验证保护的并发和写操作的作用，有更加优雅的方案去做，这一部分在新定位中属于冗余设计"

### 详细说明

当前架构的字节级验证体系包括：

```
precondition_hash  — 替换前内容哈希，防止并发修改
replacement_hash   — 替换后内容哈希
anchor_hash        — 节点锚点哈希（含前后 32 字节上下文）
content_sha256     — 源码切片内容哈希
expected-OID CAS   — Git ref 推进的乐观锁
```

用户认为在跨语言迁移定位下，这套机制是冗余的：

### 4.1 字节级验证解决的问题在跨语言场景中的实际重要性

| 字节级验证保护的问题 | 跨语言场景中的实际重要性 | 说明 |
|---|---|---|
| 同一文件并发写入冲突 | ⚠️ 降低 | 跨语言迁移中，目标文件（.py）通常是新建的，不存在多个 Slice 写同一文件的常见场景 |
| candidate 链内编辑顺序 | ⚠️ 降低 | 如果 Agent 直接写代码（第 3 点），编辑批次的概念可能变化 |
| 源文件新鲜度检测 | ⚠️ 降低 | 跨语言迁移中源文件通常只读，不参与 candidate 编辑链 |
| write scope 越界检测 | ✅ 仍需要 | 但可以用更轻量的方式实现 |

### 4.2 更优雅的替代方案

用户指出"有更加优雅的方案去做"，可能的替代方案包括（待探讨）：

| 当前机制 | 可能的替代方案 | 说明 |
|---|---|---|
| precondition_hash 字节比较 | Git tree diff + merge | 利用 Git 原生的合并能力，而非自研字节比较 |
| anchor_hash 结构定位 | 插件级 AST 定位 + 语义匹配 | 依赖插件的语言理解能力，而非字节级锚点 |
| expected-OID CAS | Git 原生 branch 操作 | 如果 Agent 直接写代码，可能不需要 candidate ref 链 |
| GuardedPatch 三哈希守卫 | 编译/测试验证 | 用验证引擎的结果保证正确性，而非写入前的哈希守卫 |

### 4.3 冗余设计的判断依据

用户认为冗余的核心逻辑：

```
当前架构的字节级验证是为"同语言内精确 AST 节点替换"设计的：
  - 同一文件内多个编辑需要字节级顺序保证
  - 同一 AST 节点的替换需要前置内容验证
  - 多个 Slice 写同一文件需要哈希冲突检测

跨语言迁移场景下：
  - 目标文件是新建的，不存在"前置内容"
  - 源文件只读，不参与编辑链
  - 不同语言文件之间不存在字节级冲突
  - 并发写入保护可以用 Git 原生机制替代
→ 字节级验证体系的投入产出比不成立
```

## 5. 当前架构需要大改的判断

### 反馈原文

> "现在的架构设计问题有很多问题，可能需要大改，和重新对齐"

### 详细说明

综合以上 4 点，用户认为当前 V3 架构存在系统性问题，不是局部修补能解决的。

### 5.1 需要重新审视的架构模块

| 模块 | 当前设计 | 问题 | 是否需要大改 |
|---|---|---|---|
| **M-00 P-01 原则** | Agent 只有提案权，不写代码 | 第 3 点否定其设计前提 | ✅ 大改 |
| **M-05 规则原语** | 4 种 AST 节点变换操作 | 第 2 点质疑表达能力不足 | ✅ 大改 |
| **M-06 AST 引擎** | NodeLocator + tree-sitter query + candidate 重定位 | 为同语言设计，跨语言需要语义级理解 | ✅ 大改 |
| **M-08 代码修改引擎** | GuardedPatch + 三哈希守卫 + 字节级编辑 | 第 3、4 点否定核心机制 | ✅ 大改或重写 |
| **M-04 Agent Loop** | Agent 输出 edit intent，不输出代码 | 第 3 点否定 | ✅ 大改 |
| **M-10 验证引擎** | 三层验证 + fingerprint 比较 | 验证引擎本身可能仍适用，但验证内容需调整 | ⚠️ 部分调整 |
| **M-07 计划生成器** | Slice DAG + write scope 冻结 | 并行机制可能仍适用，但 write scope 语义需调整 | ⚠️ 部分调整 |
| **M-03 Harness** | Run actor + DispatchAttempt + active dispatch gate | 控制面机制可能仍适用 | ⚠️ 部分调整 |
| **M-09 沙箱** | bubblewrap + validation overlay | 沙箱机制可能仍适用，但验证内容需调整 | ⚠️ 部分调整 |
| **M-11 Git 集成** | candidate ref + verified ref + expected-OID CAS | Git 机制可能仍适用，但 ref 结构需调整 | ⚠️ 部分调整 |

### 5.2 可能不需要大改的部分

以下基础设施层的设计可能不受定位变更影响：

| 模块 | 说明 |
|---|---|
| 单写者控制面（advisory lock + Run actor） | 与迁移类型无关 |
| 并行 Slice 调度（DAG ready + write scope 互斥） | 并行机制本身适用，但 write scope 语义需调整 |
| 确定性集成顺序（冻结 key） | 集成机制本身适用 |
| 沙箱执行隔离（bubblewrap + cgroup） | 隔离机制本身适用 |
| PostgreSQL 控制面 + SSE 事件投影 | 控制面机制本身适用 |
| 可观测性系统 + SecretRegistry 脱敏 | 观测机制本身适用 |
| 会话与修正编排 | 交互机制本身适用 |

### 5.3 可能的架构演进方向（待探讨）

基于以上反馈，架构可能需要朝以下方向演进：

```
当前 V3 架构（同语言迁移导向）：
  Agent 提案 → 插件生成补丁 → 字节级写入 → 三层验证

可能的 V4 架构（跨语言迁移导向）：
  Agent 直接生成目标语言代码 → Git 级写入 → 编译/测试验证
  （具体方案待重新设计）
```
