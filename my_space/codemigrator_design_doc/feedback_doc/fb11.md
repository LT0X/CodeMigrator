阶段 1：CreateRun（能力门预检，不变）
与 v5 相同：描述符摘要、grammar、镜像预检全命中 → 同一事务写 Run + 幂等 + 首个事件；初始化 Git 基线 ref。失败则三码制零副作用拒绝。

阶段 2：ANALYZE（v6 职责重定义：不再重复解析）
Run 进入 ANALYZING，但与 v5 完全不同——它不再重跑 tree-sitter 管线，只做三件事：

复用既有投影：直接装载项目注册时已建的 F1-F4 + PSF-2/3；
冻结校验：投影描述符摘要与 Spec 锁定摘要一致（断言，不重复解析）；
与已确认 UnderstandingDossier 一致性校验：用户确认的档案 vs 机械事实做一致性核对，偏差记入分析投影、不回写工件。
面试点：v5 的"ANALYZE 机械完备层 + 双怀疑派对抗审计"机制在 v6 保留（审计仍发生在签核前），但触发时点前移了——对抗审计作用在项目注册时建的那份投影上，ANALYZE 阶段不再有第二次解析。

二
两个具名常驻角色：

探索协调者（起草期）：机器骨架 → 切域调整建议（合并/拆分/重点标注 + focus brief）→ 机器校验后派发；可动态改派探索员。
EXECUTE Supervisor（执行期）：被动唤醒式常驻，只有两个职责——①归因多义/双错 → 全局修复决策；②Slice 会话失败停止 → 异常语义路由建议。（用户主动砍掉四条防御性触发："工具拒绝风暴/重试风暴/误译自动蒸馏/卡滞预警"——"现在模型性能都很强了，尽可能优雅"。）
观察模型（防止 Supervisor 上下文爆炸）：基线态势快照（机器算、不进上下文）+ 触发时定向事件投影 + 有界滚动摘要（近期保详情、远期蒸馏）。

反馈疑问：现在这个设计，为什么还有一个观察模型，这个是不是不是很优雅，现在都是主动触发了，每次都是新的agent了，只需要每次主动唤醒前要给它必要的上下文组织，这个进行讨论，如果是agent执行就可能是要进行上下文压缩的，这一部分需要进行统一，且代码复用，常驻agent的上下文压缩记得统一协调复用代码，在对整个系统有全局意识和整体理解后，再进行思考整一个设计和架构。






三
3.1 单个 Slice 的 bug → 原 Slice 自己重生成（Supervisor 不介入）
复制
集成层验证失败，证据落 A 的 write scope（唯一命中单 Slice）：
  路由判据：候选修复集 = {A}，无强耦合信号 → 简单场景
  处置：A 定向重生成 generation 1（v6 升级包：全境读视野 + 修复简报）
        → 从最新 verified 分叉 → 重译 → checkpoint → 局部验证 → 按冻结 rank 重新排队集成
        → verified 前推
  Supervisor：零介入（路由是机械判定）
谁改：A 自己的重生会话（带着归因诊断 + 前代 diff 摘要改自己的域），占 A 的 generation 0-2。

3.2 多个 Slice 的 bug（双错/跨 Slice）→ Supervisor 决策 + 全局修复会话（v6 新机制）
复制
集成层验证失败，证据同时涉及 A（order.py 签名定义处）和 C（client.py 调用处）：
  路由判据：候选修复集 = {A, C}（多义/强耦合信号）→ 复杂场景
  升级 EXECUTE Supervisor（被动唤醒）
  处置：
    Supervisor 读整体现场（已集成 A + C 候选 + 失败测试 + PSF-2 调用链 + 期望vs实际）
      → 出修复决策 Advice(REPAIR_DECISION)：
          repair_set = {A, C}
          domain_split = {A: [order.py], C: [client.py]}
          修复简报（必要输入）
    actor 白名单校验收养（免确认门，归因驱动内部闭环）
    → 派发【全局修复会话】：
        身份 (run_id, repair_decision_id)，不属于原 A/C，不占 generation 0-2
        读：全 Run verified 树 + 源快照 + 失败测试 + 修复简报（导航索引式装配）
        写：{A, C} 联合域 write scope（条件安全：A/C 已全集成，无在途写者）
    → 修 → checkpoint → 局部 → 集成 → verified 前推 → 重新最终验证
谁改：既不是 A 也不是 B，而是 Supervisor 派发的"全局修复会话"这个新 agent——它不属于原 Slice，站在全局视角同时改 A、C（联合域）。Supervisor 只出决策建议（零写权），actor 白名单收养，修复会话才是"持图纸的施工队"。 

反馈疑问：集成测试和最终测试我觉得优雅的话直接全部用这个进行处理  Supervisor，因为就算单个slice,测试这种东西都多种多样的，运行中的bug，可能并不能全部会报错，可能是不符合预期的数值，这一块，这种运行时期才知道bug，很难定义是属于那个slic，所以就直接进行统一的supervosor进行处理，我们还要设计的是如何给它构建上下文，且这个上下文要符合kv_cache的前缀，也就是说是动态维护的过程，集成一个sLic,会从上一次的调用，还是上一次的slic更新进行动态增加，新来的slic,我们要怎么给它高效上下文，这都是需要探讨的。我有一个疑问就是，假如这个集成测试失败了，关乎到多个slic，然后 Supervisor 进行修改处理了，但是修改的时候，修改完成，通过了测试了，有没有可能影响到后面并行正在运行的的slic，进行合并集成的时候，Supervisor修改的部分 造成了代码冲突，这种事情会发送吗，在对整个系统有全局意识和整体理解后，再进行思考整一个设计和架构。
