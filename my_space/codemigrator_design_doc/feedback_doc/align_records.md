## 1. 逐项对齐详情

### 1.1 Slice 修改记录与迭代记录（fb7 第 1 段）

**fb7 原文**："每个 slic 的修改记录和迭代记录都应该有，这样子修改记录可查，且代码是当前情况的事实，迭代记录和 slice 的迭代记录历史层面的事实，agent 缺少上下文的时候可以进行查看，且有一个整体的认知，应该升级到系统设计特点的层面，如何利用和治理收敛这些内容是我们设计的重要部分"

**独立核实**：M-08 已有 checkpoint commit 链（每次迭代终点 Git 提交）与逐次写操作审计账本；M-02 有 run_events 事件流；generation 0..2 重生成机制已存在。缺的是"**历史作为上下文资源**"——新 generation 会话开启时可消费前代失败诊断与 diff 摘要，这一设计地位未明文化。

**对齐过程**：R3 打包确认，用户勾选"采纳：Slice 历史治理"。

**最终决策**：升级为系统设计特点——
1. 重生成会话开启时，Context Pack 注入前代失败诊断摘要 + 前代 checkpoint diff 摘要（历史事实供给，非自由记忆）
2. "历史治理"（checkpoint 链 + 事件流 + 恢复简报）作为垂类设计特点在 M-00 成文定位

**修改清单**：M-00（特点定位一段）、M-04（重生成会话上下文构成）、M-14（历史注入与恢复简报扩展、预算边界）

### 1.2 源项目无测试套件场景（fb7 第 3 段）

**fb7 原文**："同时还有一种可能，原项目可能没有测试套件，这种个人的项目"

**独立核实**：现有设计仅处理"目标树上无测试文件"（Test 空集预派发跳过，SkippedEmpty receipt，D-033）。**源项目本身无测试时**：测试翻译 Slice 不存在 → 最终验证主证（翻译后测试通过）消失 → 等价信心分级失去行为证据。click-video 实证：后端 50+ Go 文件仅 2 个测试文件（chatgpt_test.go / trie_test.go），前端仅 1 个 App.test.js。

**对齐过程**：R1 提供三选项（诚实降级 / 测试生成 Slice / 降级+可选补测）。用户选择测试生成路线："我认为测试部分还是很重要的也是我们这个项目需要设计的重点，如果没有的话，是应该由 agent 生成测试用例，但是尽可能保证与源等价，同时需要做日志说明这一份的测试是由 agent 生成的"。

**最终决策**：Agent 生成测试用例路线——
1. 无测试模块派生**测试生成 Slice**（新 SliceKind 语义：以源模块代码语义 + 契约签名为锚点生成目标语言测试，"尽可能与源等价"= 行为锚定到源代码语义而非凭空编写）
2. **GENERATED 标注全链路贯通**：测试生成 Slice 的产出文件、CheckResult receipt、验证 fingerprint、REPORT 证据页全部显式标注 GENERATED，与移植测试严格区分
3. 等价信心分级区分两档主证：**移植测试主证**（源有测试）与**生成测试主证**（源无测试，证据力降一档并在证据页声明差异）——生成测试验证的是"翻译后代码自洽且符合源语义的 Agent 理解"，存在理解偏差风险，分级必须诚实反映

**修改清单**：M-00（SliceKind 扩展 + GENERATED 语义 + 等价分级双档）、M-04（测试生成会话上下文：源模块正文+契约签名+生成指引）、M-06（F3 对无测试模块显式标注 EmptyTestSuite）、M-07（无测试模块的测试生成 Slice 派生规则）、M-10（生成测试的验证语义：与移植测试同执行面、fingerprint 区分标注）、M-15（证据页 GENERATED 标注与双档分级展示）

**fb7 原文**："测试环节的测试应该是这个垂直 agent harness 的设计重点，这一部分需要特别的有效优雅的设计"

### 1.4 测试翻译循环依赖归因盲区（fb7 第 7 段）

**fb7 原文**："测试翻译的循环依赖问题：这是最核心的实用性问题……如何区分'测试翻译错了'和'实现翻译错了'？P-09 的归因算法试图解决这个问题（两步归因），但它的前提是'失败证据落点'能区分——这在实践中可能不成立，因为很多测试失败（如超时、OOM、断言差值）的栈信息不清晰。"

**独立核实**：M-10 已有两步归因（测试文件路径 → 失败证据落点依赖闭包判定）+ "无法唯一归属时进入 Run 级终态判断"兜底。fb7 指出的盲区属实：超时/OOM 的证据落点模糊时两步归因退化为兜底，自动化中断。

**对齐过程**：R2 提供三选项（守恒信号辅助 / 双向重生成 / 维持现状），用户选守恒信号辅助归因。

**最终决策**：D-033 结构守恒信号升级为归因辅助——
1. 失败证据模糊（超时/OOM/栈不清晰）**且**守恒离群（断言数对齐比/测试数对齐比离群）→ 优先怀疑测试翻译 Slice（断言数守恒离群=测试翻译丢断言的强信号），定向重生成测试翻译 Slice
2. 失败证据模糊**且无**守恒离群 → 优先怀疑实现 Slice
3. 仍无法判定 → 维持既有 Run 级终态兜底
4. 不新增机制：守恒计算（D-033 已有）+ 归因规则（P-09 已有）的语义升级，伏笔已埋

**修改清单**：M-10（归因规则增第三信号维度 + 验收条款）、M-00（P-09 表述同步）

### 1.5 语义鸿沟验证边界（fb7 第 8 段）

**fb7 原文**："跨语言翻译的语义鸿沟……验证层（测试通过）可以捕获功能错误，但可能无法捕获性能问题、安全漏洞或生态习惯差异。"

**独立核实**：属实——测试主证的证明范围限于源测试覆盖的行为等价；性能特征、安全漏洞引入、生态习惯差异（如 Python 侧惯用法）不在任何验证层覆盖内，且未在报告声明。

**最终决策**（R4）：边界声明 + 安全 linter——
1. REPORT 证据页增**验证边界声明**：明示"测试主证覆盖行为等价（限于源测试覆盖范围）；性能等价、安全等价、生态习惯适配不在主证证明范围"
2. 描述符 lint 档可声明安全 linter（Python 侧 bandit、Go 侧 gosec 类）作为可选辅助检查——现有五类命令模板机制的自然用法，仅文档提示用法，零机制新增

**修改清单**：M-10（验证边界声明语义）、M-15（证据页边界声明区块）、M-01（描述符示例补安全 linter 用法提示，轻量）

### 1.9 非源语言工件处理（fb7 第 14 段，与语言扩展表达力议题重合）

**fb7 原文**："项目的迁移往往涉及到的可能不止一个语言，以及多个基础设施和部署组件"（另：go-zero 生成代码 .pb.go 在 click-video 中占比很高）

**独立核实**：架构只定义了"源语言代码 + 清单文件（package.json 类）"两类输入。click-video 的 proto 文件与 .pb.go 生成代码、docker-compose.yaml、Makefile、config.yaml、SQL schema（douyin.sql）均无归属设计。其中生成代码翻译是伪命题（应从 .proto 在目标侧重新生成）。

**对齐过程**：R1 提供三选项，用户选三类工件策略。

**最终决策**：三类工件策略，入描述符声明——
1. **生成代码**（.pb.go 等）：不翻译；由目标侧从源头（.proto）用目标工具链重新生成（grpcio-tools 类命令入目标端描述符 scaffold 档）；.proto 源文件本身作为"接口事实源"被契约波消费
2. **声明式基础设施配置**（docker-compose/Makefile/config.yaml）：作为**声明式工件**由契约波 Slice 翻译（目标侧等价物：compose 改 Python 镜像、Makefile 改目标命令、config 键值映射）——归入契约 Slice 的 write scope 派生
3. **资源文件**（SQL schema、静态资源）：按描述符 mapping 的资源映射复制/轻转换，不入翻译 Slice
4. 工件分类规则由描述符声明（工件类型识别 + 各类处理策略字段），保持"语言差异=数据"不变式

**修改清单**：M-00（工件分类公共契约：ArtifactKind 枚举 + 处理策略语义）、M-01（描述符 schema 增工件策略字段 + 目录示例）、M-05（Spec/能力门对工件声明的消费）、M-06（F4 构建清单摘要扩展工件识别）、M-07（三类工件对应的 Slice 派生：生成类→契约波生成 action、声明式→契约 Slice write scope、资源类→复制任务）、M-08（生成 action 的执行侧）

### 1.10 交互形式：Spec 起草会话（fb7 第 13 段）

**fb7 原文**："交互的形式，应该是用户选定一个源项目路径，然后用户再输入对应的迁移需求。然后由 agent 书写初步所需要的文件，如果信息不足可以调用提问工具和用户对齐需求和补充信息。"

**独立核实**：现状=M-16 的 CLI migrate start（脏树 AskUser 确认）+ 手写 Spec JSON（256KiB 上限）+ 运行中风险提问。手写完整 Spec JSON 对用户不现实——fb7 指出的门槛空隙属实，且与现有 AskUser/InteractionStatus/InteractionStatus 机制天然可衔接。

**对齐过程**：R2 提供三选项，用户选 Spec 起草会话并补充："最后生成的 spec 需要给用户看完，同时也支持继续修改和对齐"。

**最终决策**：Spec 起草会话（ANALYZE 前的新交互阶段）——
1. 流程：用户选定源项目路径 → 自然语言输入迁移需求 → Agent 只读探索源项目（ReadFile/QuerySourceAst，ANALYZE 级授权）→ 起草 Spec 草稿（语言对/范围/工件策略/测试策略建议值）→ AskUser 补齐关键决策 → **用户审阅草稿全文，支持多轮修改与再对齐** → 用户显式确认后 Spec 才生效入 CreateRun 流程

### 1.11 沙箱工作模式：工作区即沙箱卷 + 结构化写 + Shell 构建（fb7 第 15 段）

**fb7 原文**："在沙箱里面的环境里面，然后里面是有完整的 shell 的，在里面构建整一个的项目，最大化发挥 agent 的能力，从而也进行约束了安全，只需要做一些必要的安全设置，防止 shell 破坏镜像，也能更加灵活的面对，构建完镜像即可在一定时间过后删除，不会造成存储的负担"

**独立核实与对齐过程**（R2-R4 三轮，本轮最深）：
- R2：用户重申设想（"在整一个的沙箱或者镜像环境里去迁移整个项目……现在的模型 agent 在 shell 的应用做的很好了"），并征求我的看法
- 我的深入分析：(a) 用户方案不破坏宿主安全（bubblewrap 边界不变、工作区 Git 可重建）；(b) 真实代价在三处——write scope 逐写拦截失效（shell 重定向不走网关）、验证确定性通道、D-034 论证重写；(c) 均有补救路径
- R3：用户确认方向（"解放 agent 能力以及虚拟环境约束的方向是没有问题的"）并追问物理形态："项目还是在宿主机上书写文件夹吗，不是整一个项目都在沙箱环境中去构建进行隔离，最后迁移完成后用户验收后再一段时间内删除，无负担"
- 我确认形态可行：每 Slice 工作区物理上就是沙箱卷（宿主共享挂载），沙箱生命周期从"单次检查"延展为"Slice 全生命周期"
- R4：工具面形态三选项，用户选"结构化写+Shell 构建"

**最终决策**：沙箱全能力工作模式（V4 执行形态演进，本轮最大架构变更）——
1. **物理形态**：每 Slice 候选工作区=沙箱卷，宿主 app 与该 Slice 专属沙箱共享挂载（Docker volume 模式）；沙箱长生命周期（Slice 创建→集成/废弃），构建缓存/已装依赖跨命令驻留（迭代加速）；集成 receipt 后销毁工作区+沙箱（"验收后删除"与既有清理语义衔接）
2. **工具面分层**：
   - 文件写读保留结构化工具（WriteFile/EditFile/ReadFile）：原子写、防半写、精细审计保持
   - 新增 **Shell 工具**（沙箱内执行）：构建/依赖安装/探索/按中间结果临场多步编排——Agent 能力最大化的通道
   - 验证检查仍走冻结模板通道（CheckRunner/InternalVerificationDispatch）：fingerprint 确定性完整保持
3. **write scope 防护转型**：从"逐写路径门拦截"（结构化工具保留此机制）+ Shell 路径新增"**checkpoint 批量校验**"——checkpoint 提交时校验工作区 Git diff 全部落在冻结 write scope 内，越界拒绝提交且工作区不污染 verified（防线从逐笔拦截变为事前（结构化）+事后（批量）双轨）
4. **审计**：Shell 命令全量记录进 run_events（命令文本+退出码+输出摘要），粒度粗于结构化工具但完整可查
5. **安全边界不变**：bubblewrap 参数、无凭据挂载、网络策略均不变；长驻不改隔离语义
6. **资源公式调整**：长驻沙箱内存驻留 × 并发数需入资源公式（4GiB×4 并发基线复核）
7. **D-034 论证重写**：M-12"为什么没有自由 shell"节改写为"为什么是分层工具面"——原四条理由中信任模型/确定性两条改述为"分层通道"论证（结构化通道保确定性，Shell 通道保能力，验证只走前者）

**修改清单（大改）**：M-08（工作区即沙箱卷物理形态、checkpoint 批量校验、生命周期）、M-09（长生命周期沙箱、Shell 执行面、资源公式、论证节改写）、M-12（Shell 工具 schema/审计/不进 fingerprint 表述、D-034 论证节重写、验收条款）、M-00（工具面分层表述、资源公式同步）、M-04（会话工具面增 Shell）、M-13（Shell 命令审计事件）、M-14（Shell 输出的上下文治理）

### 1.12 流程僵化：契约漂移修正协议（fb7 第 17 段，经 R3 澄清）

**fb7 原文**："PLAN——生成三类 Slice DAG(纯确定性) 表达能力的问题，五阶段表达能力的问题" → R3 澄清为："主要体现的是流程僵化这一方面，这样子五阶段流程是否能完成复杂的项目迁移，以及能否适应代码在设计状态和运行状态中动态的复杂度，导致的不断动态修改和推翻"

**独立核实**：现有动态修正机制=PlanRevision（运行中修正）+ generation 0..2 定向重生成 + compensation Slice（已集成结果修正）+ ImpactPreview（结构修正确认）。缺口：**契约级错误的涟漪修正**——契约 Slice 集成后发现签名/设计级错误时，全部下游实现/测试翻译 Slice 建于其上，作废重建的涟漪成本与决策门槛未定义。

**对齐过程**：R3 提供三选项，用户选契约漂移修正协议。

**最终决策**：契约漂移修正协议——
1. **涟漪成本模型**：契约 Slice 集成后触发修正时，Harness 计算下游受影响集合（直接依赖该契约的全部实现/测试翻译 Slice 及其已集成状态），产出涟漪预览（作废范围/重建范围/预计 Slice 数）
2. **用户确认门**：涟漪超过阈值（如 >N 个已集成下游 Slice）时必须经 ImpactPreview 用户确认；小涟漪（如仅未开始下游）可自动执行并记录事件
3. **执行语义**：受影响下游 Slice 作废（generation 重置或 Slice 重派，依其集成状态），契约 Slice 依既有 PlanRevision 通道重生成，重建走正常 DAG 就绪
4. 与既有 compensation Slice 的边界：compensation 处理"已集成结果的局部修正"，本协议处理"契约源头错误的波及修正"，两层衔接（契约修正→下游 compensation/作废重建）成文

**修改清单**：M-16（契约漂移修正协议设计）、M-00（修正协议的公共语义一段）、M-07（涟漪计算依赖图）、M-13（漂移事件观测）

### 1.13 多 Agent 并发与协商（fb7 第 17 段）

**fb7 原文**："尽可能的快，多个 agent 如何去协商工作，保持，怎么样的协调工作，不止是文件层面的，agent 通信层面的，但是目前的结构设计要保留。留到后面作为 baseline,对比" → R3 用户升级意见："多 agent 方向是重点设计，且是需要探讨和实现的" → R4 澄清最终所指："多 agent 协商指的是**同一个迁移任务内**的 agent 协商交互，不是多个会话（迁移任务）的交互，里面如何最大化的并发和协商机制是我们考虑的，**当前的是不是某些设计是串行的，主要的瓶颈是哪里**"

**独立核实（串行瓶颈勘察，含文档行号）**：
- **瓶颈 ① 契约波全局屏障**：[M-00 L589 V-M00-V4-001] "契约 Slice 未清空集成队列时实现波不启动"——全局屏障语义；而 Requires 边本身已是依赖闭包语义（实现 requires 其依赖模块的契约）。全局屏障无额外安全价值，仅保"两波"叙事整齐；大项目契约波长尾期间实现并发度空转
- **瓶颈 ② 测试翻译 requires 实现**：[M-07 L49] "测试翻译 Slice requires 覆盖图中全部被测模块的实现 Slice；被测实现先集成，翻译测试时语义可参照"——但测试翻译的硬输入是契约签名+源测试文件（测试测公开接口），"参照实现"是软收益；当前语义使测试翻译波整体后置于实现波，总时长=实现+测试翻译串行
- 瓶颈 ③ 集成 ref 串行推进：Git 单 ref CAS 物理约束，可接受；增量验证累积开销为可观测优化项
- 瓶颈 ④ 沙箱并发上限 4：资源公式约束；会话内串行循环为 LLM 本质

**协商机制定位分析**：V4 的协商哲学=**用数据结构协商，不用消息协商**——契约=协调媒介，集成层类型检查=冲突检测器，契约漂移修正协议（1.12）=协商通道。依赖闭包就绪即启动后，DAG 调度即并发协商主体；Agent 间 P2P 消息在本架构中无必需场景（契约歧义走漂移协议、理解不一致走类型检查），保留为未来实验方向。

**对齐过程**：R4 提供并发优化两选项打包，用户选"两项全采纳"。

**最终决策**：两项并发优化 + 协商定位成文——
1. **弱化契约波全局屏障为依赖闭包就绪即启动**：实现/测试翻译 Slice 在其全部依赖契约 Slice 集成后即可进入 RUNNING，不等全仓库契约清空；"两波"退化为拓扑层标注（观测语义同步：wave_duration 指标改为按层统计）；V-M00-V4-001 验收条款重写
2. **测试翻译并行化**：测试翻译 Slice 的 Requires 前驱从"覆盖的实现 Slice"改为"覆盖模块的契约 Slice"（翻译工作与实现并行）；其集成序仍天然后置（集成树上跑测试需要实现在场，由集成验证保序，不加新边）；总时长从 实现+测试翻译 串行变为 max(两者) 并行
3. **协商定位成文**：M-00 增"并发与协商模型"表述——数据结构协商哲学 + 两个真实瓶颈的优化记录 + P2P 消息列为未来实验方向（当前结构保留为 baseline 与 fb7 原意一致）

**修改清单**：M-00（V-M00-V4-001 重写为依赖闭包语义 + 并发协商模型表述）、M-04（波次表述同步 L158-164）、M-07（测试翻译 Requires 派生规则改契约依赖 + V-M07-V4-007 重写 + 屏障弱化的派生侧表述）、M-13（wave_duration 指标语义调整）

### 5.1.2 议题 B：PSF 项目结构底座（fb7#13，主轮开放项①展开）

**fb7 原文**："tree-sitter 是按文件逐个解析的，不存在'整个项目的一棵语法树'这种东西……这里我们有扩展的点，'整个项目的一棵语法树'，利用这个 tree 建立项目的小子树联系，联系很重要。ANALYZE 阶段细节……加载 tree-sitter-typescript.so 分析项目得到 tree"

**独立核实**：
- 用户拆解的误解属实：M-06 确为逐文件解析为不可变 AST（grammar 描述符锁定），无整项目一棵树

**对齐过程**：R1 用户要求"升级到系统层面的设计，构建完整的项目树以及之间的联系需要设计看看，当前设计是否优雅高效还需探讨"；R3 提出 PSF 三层模型提案，用户采纳。

**最终决策**：PSF（Project Structure Foundation）三层模型——
1. **PSF-1 语法森林**：逐文件不可变 AST（现状保持，进程内 LRU），子树节点在此层获得位置身份
2. **PSF-2 项目索引（新增一等结构）**：SymbolBinding（定义点 file:range + 符号类别 + 签名摘要）与 ReferenceSite（引用点 file:range，经 import 边解析归属）双向索引；由 F1+F2 确定性派生、纯代码路径；测试覆盖边升级为符号级（测试用例→被测符号，降级兼容模块级）
3. **PSF-3 关系图**：模块级复合图（import 边/覆盖边/包含边），现有 F2/F3 整合命名；消费方=Planner（Requires 派生）、漂移计算（依赖闭包）、集成序冻结
4. **设计约束**：全部确定性派生零模型裁量（P-02 不破坏）；PSF-2 是 PSF-3 的细化层而非替代（符号级服务归因/影响面/生成锚点，模块级服务规划/漂移闭包）；投影语义不变（PostgreSQL 可重建 7 天，同 snapshot OID 逐字节等价）；QuerySourceAst 四操作接口不变，goto_definition/find_references 从按需计算改为查 PSF-2 索引（更快且结果一致）
5. **收益**：P-09 归因升级符号级（减少 Run 级兜底）；契约漂移下游受影响集合精确到"引用该契约符号的模块"；测试生成 Slice 锚点获得符号级事实。**成本**：tree-sitter 查询模板扩展的纯工程量，无新机制类别

**修改清单**：M-06（PSF 三层模型+PSF-2 符号绑定表+覆盖边符号级升级，重）、M-00（PSF 公共契约定位）、M-07（归因派生符号级联动）、M-10（P-09 归因符号级）、M-16（漂移影响面符号级）、M-12（QuerySourceAst 改查索引，接口不变）

### 5.1.3 议题 C：多 Agent 协商与协调（fb8#10）

**fb8 原文**："多个 Agent 如何去协商工作、保持协调——不止是文件层面的，还有 Agent 通信层面的，当前的 agent 设计是如何进行多个 agent 工作的，在当前项目中对于 agent 读写操作的协调是怎样的"

### 5.1.4 议题 D：Exec 编排工具（fb7#14 Codemode 适配性）

**fb7 原文**："Codemode 的形式调用形式在当前项目的适配性是怎么样的，需要探讨一下"

**独立核实**：当前 EXECUTE 循环=纯串行 LLM 循环（"每一轮等于一次模型调用"，M-04），主轮 1.13 记为瓶颈④"LLM 本质"当时未处理；Codemode 形式（agent 写代码编排工具调用）与既有防护模型正交——底层每次工具调用仍逐笔过 ToolGateway，防护不降级。

**对齐过程（含用户三点疑问的解疑记录）**：
- R2 用户提问：①为什么不用原生 Rust 而嵌入 JS 引擎；②编排是一种模式还是一种工具；③Agent 如何在 Shell 与编排工具之间选择
- 解疑要点（成文素材）：①**脚本作者是模型不是开发者**——编排脚本是 LLM 运行时生成的输出数据，宿主 100% Rust，脚本在被嵌入的 JS 引擎（deno_core/rquickjs 类成熟 Rust crate）内解释执行，与 Shell 工具写 bash 同构（"原生语言"属于宿主，脚本语言按"运行时可解释+进程内可沙箱+模型生成可靠性"三标准选择，JS 三项全胜；Rust 无进程内不可信脚本执行方案）；JS 引擎数十年硬化恰好匹配信任模型——内存/CPU 上限、零环境权威、唯一出口=工具桥；②协议层是工具（closed-schema 新增 `Exec { script, timeout }` 变体）、交互层是模式（调用形式从逐轮单调用升级为可编程编排）；③选择规则"**单步直调，多步编排**"——单条命令直调 Shell，批量同构操作/多工具组合流程用 Exec 脚本（脚本内可 `await tools.shell()` 组合全部工具）；Exec 为组合超集，直调为单步最短路径，写入工具描述由模型自然遵循，无需硬性门控
- R3 解疑后用户拍板采纳

**最终决策**：采纳 Exec 编排工具——
1. EXECUTE 工具面新增 Exec：Agent 写 JS 在 app 进程内嵌入式引擎执行，`await tools.xxx()` 编排 L1-L3 工具（循环/条件/并行），一次模型调用完成多步确定性编排
2. **防护不变**：底层每次工具调用逐笔过 ToolGateway（write scope/路径门照常）；脚本零环境权威，唯一出口为工具桥；验证裁决不经 Exec（P-02 不破坏）
3. **审计**：脚本全文+逐笔回执入工具审计/run_events；V-M04-V4-013 回执溯源语义扩展（"该轮之前的回执"含 Exec 内回执序）
4. **预算**：Exec 内工具调用计入会话配额；Exec 单次超时按模型工具档；脚本错误=一次可自纠的工具失败（错误回上下文，模型改脚本重试）
5. **与 Shell 正交**：Shell=能力通道（能做什么），Exec=编排通道（多少次模型调用做完）——串行 LLM 循环瓶颈④的解法；工具面终态六件（见 5.1.5）
6. 典型场景：批量源结构探索（20 轮变 1 轮）、契约变更后跨文件一致性修订、查→读→改→shell 验证组合流程、测试生成批量产出

**修改清单**：M-12（Exec 工具设计：schema/引擎选型/工具桥/超时预算/审计，重）、M-04（六工具面+调用形式+验收条款重写，重）、M-08/M-09（执行面：引擎 app 进程内、Shell 调用入沙箱、引擎资源开销）、M-13（编排审计事件）、M-14（Exec 结果上下文治理）、M-00（工具面分层表述+资源公式含引擎开销）

### 5.1.5 议题 E：验证通道待定重开——自检并入 Shell，CheckRunner 退役（修订主轮 1.11 部分结论）

**fb7 续轮原文**："沙箱工作模式：工作区即沙箱卷 + 结构化写 + Shell 构建（fb7 第 15 段）验证检查仍走冻结模板通道（CheckRunner/InternalVerificationDispatch）：这一部分待定"

**独立核实**：
- **双路径尴尬**：主轮 1.11 拍板后，Agent 的检查执行存在两条并行路径——CheckRunner 自检走 UDS 派发+一次性 overlay（候选工作区受控快照，前 fb7 时代遗产：当时工作区是宿主受信目录需 overlay 防污染）；Shell 走长驻沙箱卷直接执行。两者认识论地位相同（反馈不裁决、不进 fingerprint）但执行基础设施完全不同；fb7 后工作区即沙箱卷，Agent 已能在其中自由构建，overlay 隔离的自检价值大幅弱化（污染本就发生在沙箱内，由 checkpoint 批量校验兜底）
- **两层冻结理由不对称**：裁决层冻结不可妥协（Agent 若能影响检查集选择="自选考题"，fingerprint 失去独立性，P-02 根基；且裁决对象是 tested_commit_oid 的 Git tree overlay，与候选工作区无关）；自检层冻结是软性理由（结构化诊断+与验证层同命令面叙事）
- 裁决层 InternalVerificationDispatch 非 Verify 阶段工具、不在 phase-tool policy 注册，不受 Agent 工具面变化影响

**对齐过程**：R2 呈双路径尴尬与不对称分层分析（按用户"释放能力+优雅简洁工具集"原则推导四层工具面），用户拍板"自检并入 Shell（推荐）"。

**最终决策**：自检并入 Shell，CheckRunner 退役——
1. **CheckRunner 作为 Agent 工具退役**：会话自检走 Shell（自由命令自由参数，长驻沙箱内执行，构建缓存/依赖驻留复用）
2. **裁决层唯一保留冻结模板通道**：InternalVerificationDispatch 冻结检查集+tested_commit overlay→fingerprint 完整保持；UDS 派发链消费者更新为"裁决层+Scaffold"两项；描述符命令模板的模型侧消费者清零（联动议题 A）
3. **损失确认**：放弃 CheckRunner 结构化诊断（DiagnosticMapping file:line）与"会话自检与验证层同命令面"叙事——验证独立性本就不依赖自检同面（裁决永远由冻结检查集独立做出），模型读原始输出自纠
4. **D-034 取代关系记录**：CheckRunner 的 Test action+test_filter 有界参数路线被 Shell 自由命令取代
5. **工具面终态六件（四层）**：

```

L2 结构化导航     QuerySourceAst                    （源快照符号级只读导航，查 PSF-2 索引）
L3 能力通道       Shell                             （长驻沙箱内自由执行：构建/依赖/探索/自检）
L4 编排通道       Exec                              （嵌入式 JS 引擎编排 L1-L3，一次模型调用多步执行）
──────────────────────────────────────────────────
裁决层（非模型工具）InternalVerificationDispatch      （冻结检查集+tested_commit overlay→fingerprint，唯一冻结通道）
```

6. write scope 防护双轨保持（主轮 1.11）：结构化工具逐写拦截 + Shell 路径 checkpoint 批量校验；Exec 编排的底层调用逐笔过网关（防护不变）

## 8.2 两议题处置决策（用户拍板过程）

**议题一：ANALYZE/PLAN 零裁量质疑 → 架构升格为「理解先行」双层协作**
- 用户立场演进：质疑 tree-sitter 作为唯一信息原点的失真/不完备风险 → 不信任其可构建项目级联系树 → 要求 ANALYZE/PLAN 的 agent 成为设计重点；明确目标函数：更好的 agent 信息、更低 token 与决策成本、优雅高效、垂类差异化。
- 探索中排除的方向：仅顾问化（不回应根本担忧）；模型直拟 DAG（放弃计划可复算性，P-02/P-03 重写代价过大）。
- **定案**：机械完备层（tree-sitter/清单解析保留为完备性引擎+位置锚点，枚举保底不漏——其枚举能力恰是被信任部分）× 语义消解层（ANALYZE Reasoning 理解会话在完备候选集上定向探索，产出《项目理解档案》UnderstandingDossier 一等公民工件：语义模块划分/依赖消解判定/测试地图/风险热点/策略建议，全条目 file:range 锚点+覆盖率自述）× 用户确认门（档案随 Spec 草稿一并审阅，确认后 hash 冻结为 Run 第三件输入）。PLAN 从三件冻结输入机械派生不变——同快照+同 Spec+同档案必得同计划；模型智能经"档案+用户确认"正门进入规划。
- 完整性的诚实拆分：枚举完整=机械层保证（Agent 做不到也不需要它做）；语义正确=Agent+用户层保证（机械做不到）；token 经济=一次 Reasoning 蒸馏换 N 个执行 Slice 免盲探，存在盈亏平衡点故档案分 Shallow/Deep 预算档。

**议题二：AST/CST 选型 → 成文选型边界**
tree-sitter CST 只读采用（读代码/定位切片/锚定）；改写归 EXECUTE Agent 文本直写（V3 改写链废除史引用）；原生单语言 AST 引擎不引入（语言绑定税/构建前提/职责错位三重理由成文于 M-06 选型边界小节）；`semantic_service` 留演进面设想不做承诺。

# 10. 依赖地图与并发量级对齐（2026-08-23，D-040）：完备性对抗审计 + 三池模型

> 触发来源：用户三问——①博客的依赖地图到底怎么产生、是否实录；②本库确定性脚本"弱"、依赖 tree-sitter 是否站得住；③博客可做到 12~数百子代理并发，本库为何只有个位数。经抓取 claude.com 博客全文、starter kit 原始提示词（prompts/01-dependency-map.md 等）、Jarred 本人博客（bun.com/blog/bun-in-rust）与 kit README 三方交叉核查后对齐。

## 10.1 事实核查结论

- starter kit README 自证出处性质："these prompts are **reconstructions** — generalized and reviewed against real production migrations... **not transcripts**"；Bun 实际工件"messier"：576 行 PORTING.md 规则书 + 一句话 kickoff。

## 10.2 两项决策（用户拍板）

1. **依赖地图补强**：吸收 kit 的「双怀疑派抽样审计」闭环入 M-06（独立上下文×不相交样本[随机半+对抗指派半]×file:line 证据行×双向 diff×修提取规则不修结果×三轮上限升级用户）；显式成文 SCC/环拒绝在模块粒度执行（强于 kit 文件级+后收缩）。零新机制，纯运营流程。
2. **并发架构升格为三池模型**：资源公式不再约束模型会话数——`min(4,…)` 改判为**同时活跃 bwrap 沙箱执行位**的上限（Shell/Scaffold/一次性检查按需取用归还）；模型会话池（只读工具+LLM 调用不经沙箱）由 provider 配额与 Run 预算约束，可支撑数十路扇出；裁决派发池维持 active-attempt gate。安全性不减：bwrap 只罩不可信执行。依据：Bun 64 路实战验证量级；本库只读工具本就不经沙箱，旧公式把三类异质资源捆一池属过度保守。
