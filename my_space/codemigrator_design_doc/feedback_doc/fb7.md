二、核心实用性问题（质疑与风险）

1. 测试翻译的循环依赖问题【标注为：最核心的实用性问题】
   架构的声明：“翻译后测试套件通过是语义等价主证据”
   但测试本身也是从源语言翻译过来的，由此产生悖论：
   如果测试翻译错了（如断言语义变了）→ 测试通过不能证明语义等价
   如果测试翻译对了 → 测试失败可能反映实现翻译错误
   核心难点：如何区分“测试翻译错了”和“实现翻译错了”？
   P-09 的归因算法（两步归因）试图解决此问题，但其前提是“失败证据落点”能被区分——这在实践中可能不成立
   原因：很多测试失败（如超时、OOM、断言差值）的栈信息不清晰
2. 跨语言翻译的语义鸿沟
   TypeScript 和 Python 之间的根本性差异：
   TypeScript 有类型系统但编译后消失；Python 是纯动态
   TypeScript 有 async/await 和 Promise；Python 有 asyncio
   TypeScript 有 enum、namespace、装饰器；Python 有不同的实现方式
   架构层面的担忧：
   架构把这些问题全部交给 Agent 处理，但 Agent 的翻译质量是不确定的
   验证层（测试通过）可以捕获功能错误，但可能无法捕获：性能问题、安全漏洞、生态习惯差异
3. CheckRunner 自检的实用价值（存疑）
   现状：Agent 可以在会话内运行 CheckRunner 进行自检
   局限：CheckRunner 跑的是“语法检查 + 类型检查 + lint”
   对跨语言翻译场景，这些检查能发现的问题有限：
   Python 语法检查通过只说明代码是合法的 Python，不说明它等价于原来的 TypeScript 代码
   真正的语义等价验证只能靠测试，而测试在验证层才跑
4. PLAN 阶段 / 五阶段的表达能力问题
