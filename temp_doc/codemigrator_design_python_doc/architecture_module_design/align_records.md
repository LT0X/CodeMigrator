## 1. 首篇记录 · 2026-08-27：fb.txt 批评对齐与 V5 架构方向定稿

### 1.1 对齐背景

用户依据实践需要提出对齐反馈（fb.txt，本目录内），对 V4 基线提出五点核心批评：

1. **多 Agent 探索缺失**：起草会话单 Agent 只读探索（ReadFile/QuerySourceAst/Exec 只读编排）——是否考虑多 Agent 探索，交互与总结是可设计的点；
2. **导航地图参照**：tree-sitter 导航地图可参考 colbymchenry/codegraph；
3. **Slice 范围死板**：迁移项目的项目文件夹与各类 Slice 切片"似乎写死"、各 Slice 限定范围如何确立——修改可能涉及多个文件夹代码，写死项目文件夹的方向需要重新考虑；
4. **确定性 DAG 拧巴**：从三件冻结输入（快照 + Spec + 已确认档案）确定性生成 DAG——"靠写死文件夹实现这个不要也罢，可以引入大模型，现在的设计很拧巴且死板，一点都不优雅"；
5. **工具与安全参照 pi agent**：打算工具和安全层面参照 pi agent 设计，顶多加垂类场景优化工具；总结论："感觉得来 V5 重构了"。

对齐前外部调研结论：

| 参照 | 调研结论 |
|---|---|
| **pi agent**（pi.dev） | 极简内核（"整个核心装得进脑子"）；**无内置沙箱是诚实设计而非缺失**——进程内部分沙箱易被误解为安全边界，真实隔离交给 OS/容器边界（Seatbelt/Bubblewrap/微 VM）；项目信任只做输入加载防护；分层安全 = 硬沙箱 → 权限门 → 范围治理 → 经济断路器 |
| **codegraph**（colbymchenry/codegraph） | tree-sitter → SQLite 知识图谱：符号节点（函数/类/方法/路由等）+ 关系边（calls/imports/extends/references，带 provenance 分级）+ FTS5 模糊符号搜索；提供 callers/callees/impact/context 查询；实测（7 个真实代码库中位）平均省 35% 成本、71% 工具调用、46% 时间——探索成本前置成一次可复用索引后显著下降 |

### 1.2 对齐过程：六个决策点

按影响排序逐点对齐，每点给出分析、选项与最终决策。

**决策 1：V5 哲学定位——"裁判保留，建筑师放开"+ 垂类技术优化**

- 分析：V4 把"确定性"同时用在两个性质不同的层上——**验证层（裁判）**：翻译后测试主证、冻结检查集、fingerprint，是产品护城河（fb.txt 未批评此层）；**规划层（建筑师）**：冻结 DAG、描述符目录模板、write scope 机械派生、三件输入冻结仪式，fb.txt 的"死板"全部落在此层。fb8 给规划层开的门（档案 `semantic_modules`）太窄：LLM 只能建议分组，目标结构模板与路径映射仍由描述符机械决定——智能进入路径被稀释，这是"拧巴"的机制性来源。口诀：**确定性应该当裁判，不该当建筑师**。
- 决策：验证层确定性 Oracle 全保留；规划/探索/结构层全面 LLM 化；设计必须体现迁移垂类技术优化（不是通用 agent + 通用安全的包装）。

**决策 2：契约先行——契约层保留但 LLM 化**

- 决策：契约 Slice 从"结构性必设"变为 **Planner 的设计手段**（LLM 决定切法、内容、桩形式、是否需要）；机器校验 DAG 性质不变；依赖闭包就绪即启动保留。
- 理由：契约先行（类型桩作为并行翻译对齐基准）是真正的垂类优化手段——保留能力，去除结构刚性。

**决策 3：执行期计划刚性——冻结 + 修正协议门**

- 决策：计划确认后冻结；运行中变更统一走修正协议（M-16 演化）：安全点暂停 → 分类 → 影响预览 → 用户确认 → 重规划未集成部分；已集成 verified 永不回写。
- 理由：机制最简，与无人值守批次语义匹配（与决策 6 的"后期放手"呼应）。

**决策 4：多 Agent 探索——域分工扇出（最小档）**

- 交互设计：子会话间**零消息直连**，唯一共享介质是**只读预索引知识图谱**（延续 V4"用数据结构协商，不用消息协商"哲学）；每个探索员产出结构化探索报告（全条目 file:range 锚点 + 置信理由，与档案条目同构）。
- 总结/归并设计：**主起草会话单点归并**（档案保持唯一产出点）；冲突显式标记进草稿（不静默择一）交用户裁决；覆盖率聚合自述（各员触达清单并集 + 未读区声明）。
- 扇出深度：选**域分工扇出（最小档）**——Harness 按图谱模块域/目录域分派 N 个域探索员，各自独立上下文域内自由探索。click-video 型项目足够；大项目视靶场效果再升级（域×lens 叠加扇出、对抗审计闭环为后备升级路径）。

**决策 5：执行基座——内联 bwrap（极简）+ 并发隔离设计**

- 决策：去独立 sandbox-worker 进程与 UDS Protobuf 六方法协议，app 直接管理 bwrap（PDEATHSIG + cgroup 清理）；Shell 长驻沙箱卷保留（构建缓存跨命令复用，垂类优化）；验证在 tested commit 临时物化目录执行（替代 overlay grant 体系）；部署拓扑从 app + worker + PostgreSQL 三服务降为 **app + PostgreSQL 两服务**。
- 安全架构 = pi 四层分层模型的垂类实例化：硬沙箱（bwrap 执行不可信代码——翻译后测试必须跑，此层不可省，pi 的"无内置沙箱"哲学不可照搬）→ 权限门（phase policy）→ 范围治理（write scope）→ 经济断路器（预算治理）。
- **并发隔离设计**（响应对齐中用户追问"怎么保证 agent 不会互相串、怎么并发"）：
  - 核心论点：**隔离从来不来自 worker 进程，而来自 bwrap namespace + 计划期机器校验**——worker 只是执行外包者，把 bwrap 的 spawn 从 worker 移到 app，每个实例的 namespace 隔离性质不变，内联零削弱。
  - 四维防串：**文件互串**（每 Slice generation 独立沙箱卷为独立可写根，挂载面只见本卷；write scope 两两互斥由机器校验器在计划冻结期保证）；**上下文互串**（ReadFile 可读根按会话身份绑定：源快照 + 已集成契约 + 本 Slice 卷）；**进程互串**（每 bwrap 实例 `--unshare-all`：独立 PID/mount/IPC namespace，agent 看不到彼此进程）；**网络互串**（独立 netns，唯一出口是依赖安装代理的域名白名单）。
  - 第五道防线（事实汇合点）：并行只发生在候选生成；集成是**单写者串行**——verified ref 以 expected-OID CAS 推进，即使前四道全被绕过，唯一能污染主线的入口只有一个且受 Git CAS 保护。
  - 并发治理：沙箱执行池（活跃 bwrap 实例数受物理公式约束，每实例独立 cgroup）+ 模型会话池（provider 配额与预算，不经沙箱）。
- 工具面：封闭六工具保持（安全审计面小）+ `QuerySourceAst` 升级为**图谱导航工具**（符号查找 + callers/callees 调用图 + FTS 模糊搜索 + impact 影响分析）；`Exec` 编排保留（串行 LLM 循环瓶颈的垂类解法，pi 没有的）；不引入 pi 的开放扩展生态（迁移引擎是产品不是平台）。

**决策 6：委派模型——前期做足、后期放手（用户修订收尾）**

- 背景：用户明确修订——不希望逐个确认每个 Slice 的范围；希望在前期做足对齐工作，后期很少介入，除了中途修改。
- 决策：用户介入点收敛为**仅两处**——① 起草期四件工件确认（Spec / 理解档案 / 目标蓝图 / 规则手册，多轮深潜审阅，做足对齐）；② 运行中结构修正 / 契约漂移的 ImpactPreview 确认门（触及已集成成果时才出现）。
- 规划期全自动：LLM Planner 消费四件冻结输入（蓝图含划分原则：模块边界 / 粒度偏好 / 并行度）→ 机器校验四重确定性护栏 → 计划自动冻结生效，零用户介入。
- 核心机制：**蓝图即委派权威**——机器校验器新增"蓝图符合性"检查（write scope ⊆ 蓝图目标结构路径域，确定性可查），用户的前期对齐自动约束全部后续规划，无需逐条确认。
- 对齐链总结：**用户定原则（蓝图）→ LLM 出方案（Planner）→ 机器保安全（校验器）→ 裁判定对错（测试主证）**——四层各司其职，用户只在头尾出现。

### 1.3 V5 骨架定稿

```
【起草期】多 Agent 理解与设计
  预索引知识图谱（codegraph 式：符号 + 调用图 + FTS + impact）★垂类
  Harness 域分工扇出 N 个探索员（独立上下文、零直连、共享只读图谱）
  主起草会话归并（冲突显式标记交用户裁决）→ 四件工件：
    Spec（语言对 + 检查集 + 预算）/ 理解档案 / ★目标项目蓝图（新）/ 规则手册
  用户确认 → 冻结为 Run 输入

【规划期】LLM 建筑师 + 机器校验器 ★垂类
  LLM Planner 消费冻结输入 → 提议：Slice 集合（可含契约 Slice——设计手段非结构强制）
    + 各 Slice write scope + DAG
  机器校验器（确定性护栏，四重）：
    互斥性（write scope 两两不相交）/ 蓝图符合性（⊆ 蓝图目标结构路径域）
    / 源覆盖完备（纳入范围的每个源文件恰被一个 Slice 声明）/ 无环 + 规模上限
  校验通过 → 计划自动冻结生效（零用户介入）

【执行期】pi 式工具面 + 内联 bwrap
  封闭六工具 + 图谱导航增强 + Exec 编排；phase policy / write scope / 预算断路器
  每 Slice 长驻沙箱卷（构建缓存复用★垂类）；app + PostgreSQL 两服务拓扑
  checkpoint → verified 单写者集成（Git CAS）

【验证期】确定性裁判（不变）★护城河
  三层验证 / 翻译后测试主证 / fingerprint / flaky 归一 / P-09 符号级归因
  守恒信号 / 行为 parity / 证据链 / GENERATED 双档 ★垂类

【修正协议】骨架保留（M-16 演化）
  安全点暂停 → 分类 → ImpactPreview → 用户确认 → 重规划未集成部分
  涟漪计算图基础升级为图谱 impact 查询
```

## 2. 文档同步实施记录 · 2026-08-28

### 2.1 已同步的公共口径

- 起草阶段由预索引知识图谱支持按模块/目录域的只读多 Agent 探索；子会话不直接通信，报告必须有 file:range 锚点、覆盖率和置信度理由；主会话合并并显式报告冲突。
- 起草确认包固定为 MigrationSpec、UnderstandingDossier、TargetProjectBlueprint、MigrationRulebook 四件工件；用户确认点收敛为四工件确认、运行期结构修正/契约漂移 ImpactPreview 确认。
- LLM Planner 消费四件冻结输入与 M-06 事实，提出 Slice、边、write scope 和 integration_rank；机器校验检查范围互斥、Blueprint 合规、源文件恰好一次覆盖、无环及规模上限，成功后自动冻结，不逐 Slice 询问用户。
- app 直接管理 bwrap（PDEATHSIG、cgroup、命名空间）；Slice 长期沙箱卷跨命令保留缓存，Oracle 验证从 tested commit 临时物化目录执行；独立 sandbox-worker、UDS Protobuf 六方法和 overlay grant 退场。
- 三池模型、Graph navigation、Exec、六工具、Git/CAS 单写者、Rulebook 受控追加、Oracle 三层验证、GENERATED/LOW_QUALITY、flaky、parity、结构守恒与测试执行保序保持。
